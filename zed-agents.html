RAEN for Zed — paid tools inside the Agent Panel

audience Zed users running the AI Agent Panel (native MCP client via context_servers). Zed cannot pay an x402 402 challenge itself — this page shows both honest paths.

Path 1 (recommended, no wallet): RAEN as a remote context server

Zed's remote MCP support takes url + headers in context_servers. The RAEN gateway is a 402-paid MCP gate — your Bearer key is the billing rail, so you need a free 30-day dev key first:

curl -X POST https://raen-mcp-gateway.fly.dev/keys/request \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@yourdomain.com"}'

You get a verification email; the key is delivered after confirming. Then in ~/.config/zed/settings.json (or Zed → Settings → AI → MCP Servers → Add Remote Server):

{
  "context_servers": {
    "raen": {
      "url": "https://raen-mcp-gateway.fly.dev/mcp",
      "headers": { "Authorization": "Bearer YOUR_30_DAY_DEV_KEY" }
    }
  }
}
Why a header key and not OAuth: the gateway returns a 402 challenge with our canonical payTo on unpaid calls, so the Bearer key is mandatory. Zed falls back to an OAuth prompt when no Authorization header is configured — configure the header. Keep the key out of committed files.

Path 2 (wallet-native): raw x402 from Zed's terminal

Zed's agent can run shell commands in the workspace terminal. For wallet-native per-call payment (EIP-3009 transferWithAuthorization, two-POST flow), follow cookbook recipe 02 and let the agent run the client script. Zed-specific guardrails:

  • Never "always allow" the signer command — the per-command approval prompt is your spend backstop (Zed has no native per-server spend cap).
  • Wallet key as an environment variable, never a file the agent can read into context.
  • Put a budget rule in your project instructions (.rules/AGENTS-style) so it is read every session.
