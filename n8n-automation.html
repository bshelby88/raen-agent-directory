How a call works from an HTTP Request node

x402 is a two-POST dance. Your first POST gets an HTTP 402 with a payment-required header — a challenge naming the price and payee. You (or your agent/wallet helper) sign a USDC transferWithAuthorization on Base and re-send the POST with a PAYMENT-SIGNATURE header. The response is your JSON payload.

POST https://contract-eye-x402.fly.dev/api/analyze-contract
Content-Type: application/json

{ "text": "<your contract text, 50-50000 chars>",
  "focus": ["renewal","liability"] }
→ 402 + payment-required header (challenge)
→ sign & resend with PAYMENT-SIGNATURE header
→ 200 { risk_score, flagged_clauses[], suggested_edits }

In n8n: an HTTP Request node for the first call, your wallet/signer step in between, a second HTTP Request node with the signature header. In Make/Zapier: same pattern with a custom webhook or Code step for signing. If you already run an AI agent with an x402-compatible wallet, it just works.

Why this shape beats an API-key subscription

  • Zero commitment: pay 1¢ when the flow runs; pay nothing when it doesn't.
  • No onboarding wall: no dashboard, no email, no key rotation. The payment IS the auth.
  • Auditable spend: every payment is an on-chain USDC transfer on Base you can reconcile.
  • Agent-friendly: the same endpoints serve autonomous agents — your workflows and your agents call the identical surface.
