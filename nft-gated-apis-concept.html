CONCEPT — NOT BUILT · NOT SHIPPED · PENDING OWNER DECISION

NFT-gated paid APIs

Diamond Pass as the front door to RAEN's paid endpoints. The one NFT perk model that survives securities law — because it sells access, not returns.

The mechanism (as designed, not as deployed)

  1. A paid x402 endpoint (already live across RAEN's 11 quote-fixed surfaces) checks the payer's wallet at settlement time.
  2. If the wallet holds a Diamond Pass token from 0xAE0B6C3b…2233 on Base, the 402 challenge is issued at a discounted rate — or waived for an allocation of calls per period.
  3. Verification is a plain balanceOf read. No custody, no staking, no wallet connection on our side. The pass never moves; it just opens the door.
  4. The concierge worker written for the original Diamond project (gemini-concierge — tested, never deployed) is the template for the gated support tier.

Why this shape

Howey-safe: the token grants a service discount — the same thing a Costco card does. A buyer's upside is cheaper API calls, never a share of RAEN's revenue or a speculative floor we'd have to defend. There is no yield, no distribution, no profit promise anywhere in the design, and there never will be.

Actually compatible with x402: the pass rides the payment flow we already run instead of adding a parallel auth stack. Machine-wallet agents holding a pass get perks automatically; everyone else pays list price. No new checkout, no new accounts.

Honest open questions (why this is still a concept)

  • Demand: external revenue all-time is $0.00. Discounting access to something nobody buys yet discounts nothing. The concept only makes sense after a paid endpoint has real paying strangers — the same Phase-0 gate that killed the original Diamond Pass for good reason.
  • Listing decision: the 22 minted tokens have zero marketplace presence. Perk-gating works without any listing, but a launch sequence needs to be decided before any perk is promised publicly.
  • Whitelist math: free-call allocations must be capped server-side; unbounded free access to a paid API is how a perk becomes a liability.
  • Legal hygiene: even access-only framing needs the same no-yield language on every surface, including the marketplace listing (if one ever happens).

TRUTH: nothing on this page is a product, a promise, or a commitment. It is a design memo published early, in public, so the decision gets made in daylight. If the owner greenlights it, the build page will replace this one and say "shipped." Until then, this banner stays.

Machine buy block — x402 per-call SKUs (Base USDC, eip155:8453, scheme exact)

Payment IS auth. Two-POST flow: (1) POST without payment → HTTP 402 challenge (EIP-3005, EIP-3009 transferWithAuthorization); (2) re-send the same POST with the signed quote in the PAYMENT-SIGNATURE header → 200 + result. No API keys, no accounts, per-call USDC settlement on Base. Manifest prices below fetched 2026-11-16.

Payments CORS path / headers: Access-Control-Allow-Origin: * is set on /api/* POST routes (so agent SDKs can cross-origin fetch the paid endpoints); the client must also send PAYMENT-SIGNATURE (EIP-3005/EIP-3009 signed quote) — the header is required, not optional.
