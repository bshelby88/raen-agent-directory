Path 2: wallet-native x402 from the sandbox terminal

OpenHands agents run bash and Python inside their sandbox, so a plain script pays for the endpoint directly from a Base wallet — no gateway key. The two-POST flow:

# --- inside the OpenHands sandbox ---
import json, requests

def x402_call(url, body, signer):
    r = requests.post(url, json=body)          # 1st POST -> 402 challenge
    if r.status_code != 402:
        return r.json()
    challenge = json.loads(r.headers["payment-required"])  # accepts[]
    # 2) sign the exact-scheme challenge with your Base wallet (EIP-3009
    #    transferWithAuthorization on USDC), then re-send with the payment header
    sig = signer.sign_challenge(challenge)
    r2 = requests.post(url, json=body, headers={"PAYMENT-SIGNATURE": sig})
    return r2.json()

# OpenHands terminal step: python /workspace/x402_call.py --law-lookup "FDCPA 1692g"

Any EIP-3009 signer works. Copy-paste client recipes: x402-cookbook (recipe 02 is the Python client).

Why OpenHands fits

OpenHands speaks MCP natively (SSE, streamable HTTP, and stdio transports), so Path 1 is a single openhands mcp add command — the tools show up in every conversation with no client library. Path 2 is uniquely clean here: because the agent already executes code in its own sandbox, the two-POST EIP-3009 flow is just another script the agent can read, adapt, and run — payment stays wallet-native with zero glue code. If you outgrow the metered gateway key, the endpoint catalog above prices out identical on both paths.
