1 — Daily self-ping drift-check workflow

Save as .github/workflows/x402-daily-ping.yml. Runs daily off-schedule; alerts by email on any failure. Adapt the ENTRIES table to your apps/endpoints/amounts.

name: x402 daily self-ping

# Verifies every paid endpoint daily:
#   1. /health returns 200 (also wakes suspended Fly machines)
#   2. POST /api/* returns 402 with a payment-required header
#   3. Decoded 402 metadata matches expected network + amount + payTo
# Fails the workflow on drift → GitHub emails you automatically.

on:
  schedule:
    - cron: '37 9 * * *'   # daily, off-minute to dodge fleet collisions
  workflow_dispatch:

jobs:
  ping:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: Health + 402 drift check
        run: |
          set -uo pipefail
          declare -a ENTRIES=(
            "my-service-1   /api/thing-a   50000"
            "my-service-2   /api/thing-b   20000"
          )
          PAYTO="0xYourPayToAddressHere"
          FAIL=0
          for entry in "${ENTRIES[@]}"; do
            read -r app endpoint expected_amount <<< "$entry"
            url="https://$app.fly.dev"

            health=$(curl -sS -m 30 -o /dev/null -w "%{http_code}" "$url/health" || echo "ERR")
            if [ "$health" != "200" ]; then
              echo "::error::$app — health=$health"; FAIL=1; continue
            fi

            hdr=$(curl -sS -m 15 -I -X POST "$url$endpoint" \
              -H 'content-type: application/json' 2>/dev/null \
              | grep -i '^payment-required:' | awk '{print $2}' | tr -d '\r')
            if [ -z "$hdr" ]; then
              echo "::error::$app — no payment-required header"; FAIL=1; continue
            fi

            decoded=$(echo "$hdr" | base64 -d 2>/dev/null)
            net=$(echo "$decoded" | python3 -c "import sys,json; print(json.load(sys.stdin)['accepts'][0]['network'])")
            amount=$(echo "$decoded" | python3 -c "import sys,json; print(json.load(sys.stdin)['accepts'][0]['amount'])")
            payto=$(echo "$decoded" | python3 -c "import sys,json; print(json.load(sys.stdin)['accepts'][0]['payTo'])")

            if [ "$net" != "eip155:8453" ]; then
              echo "::error::$app DRIFT — network=$net (want eip155:8453)"; FAIL=1; continue
            fi
            if [ "$amount" != "$expected_amount" ]; then
              echo "::error::$app DRIFT — amount=$amount (want $expected_amount)"; FAIL=1; continue
            fi
            if [ "$payto" != "$PAYTO" ]; then
              echo "::error::$app DRIFT — payTo=$payto (want $PAYTO)"; FAIL=1; continue
            fi
            echo "OK $app $endpoint amount=$amount"
          done
          exit $FAIL
Why the live-challenge decode matters: your x402.json manifest can lie. A hardcoded constant in the route can diverge from the advertised manifest — a stale payTo silently misroutes every payment. Always verify what the live 402 challenge says, not what the manifest claims. Also: flyctl secrets set does not refresh a running machine's environment — a config fix isn't real until the live challenge reflects it.

2 — The Cold-Start Runbook (deploy → first payer)

  1. Health route: GET /health returning 200 + service identity. Fly suspends idle machines; a health ping (above workflow, or UptimeRobot) wakes them and keeps you discoverable.
  2. Manifest: /.well-known/x402.json with exact scheme, network: eip155:8453, correct payTo, and a description that states precisely what the paid call returns (caveats included). Overpromising here kills trust before the first refund does.
  3. Schema consistency — three surfaces must agree: (a) request fields in the manifest, (b) your OpenAPI spec, (c) what the live route actually validates. Probe with a deliberately wrong body and read the 400 message. Docs naming a field the route rejects kill the buyer before they see a price.
  4. Two-POST flow: every x402 buyer does POST (get 402 + payment-required header) → sign payment → POST with X-PAYMENT header. Test this path yourself end-to-end with a funded wallet before listing anywhere. A 200 response with a degraded: true marker is worse than an error — buyers paid for the advertised output.
  5. Telemetry: log every challenge and settle with tx hash; gate "settled" on tx presence. Counting any 200-with-payment-header as settled is the classic phantom-revenue bug.
  6. Distribution checklist (S-B rule: no deploy without it): publish llms.txt + agent-readable docs; list in the x402 Bazaar (manifest is auto-crawled); submit to awesome-x402; write a quickstart page for the exact audience that would buy. Deployment without distribution is banned by process.
  7. Ledger honesty: publish a public sales ledger (even at $0). Silence is how fake revenue survives.
