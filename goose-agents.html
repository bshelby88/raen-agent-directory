Paid API tools for Goose agents (x402 · Base USDC)

Goose — Block's open-source on-machine agent (CLI + Desktop) — pays per call for real work: no API keys, no signups, no monthly plans. Goose is MCP-native, so the fastest path is RAEN's Bearer-gated MCP gateway as a remote extension. Everything below accepts USDC on Base via the x402 HTTP-native payment protocol.

Path 1 (recommended): the RAEN MCP gateway as a Goose extension

The gateway exposes 5 tools: raen_law_lookup ($0.05), raen_ticker_analysis ($0.05, synthetic demo — see caveats), raen_dispute_letter ($0.75), raen_image_generate ($0.01), raen_contract_analysis ($0.05).

  1. Get a free 30-day dev key (self-serve, email verification, no waiting): 
    curl -X POST https://raen-mcp-gateway.fly.dev/keys/request \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.org"}'
    Rate limit 3/day/IP. The key arrives by email; export it before starting Goose.
  2. Add the extension to ~/.config/goose/config.yaml (Windows: %APPDATA%\Block\goose\config\config.yaml): 
    extensions:
  raen:
    enabled: true
    type: streamable_http
    name: raen
    uri: https://raen-mcp-gateway.fly.dev/mcp
    headers:
      Authorization: Bearer ${RAEN_DEV_KEY}
    env_keys:
      - RAEN_DEV_KEY
    timeout: 300
    env_keys keeps the key out of the config file — Goose substitutes it from the shell environment at connect time (same pattern the Goose docs use for API-key auth). Restart Goose; the tools appear alongside its built-ins.
  3. Ask Goose something real: "Look up the FDCPA citations for repeated calls about a debt I already disputed" — Goose calls raen_law_lookup and pays the per-call price from the gateway metering.

Alternative UI path: goose configure → Add Extension → Remote Extension (Streamable HTTP), URI https://raen-mcp-gateway.fly.dev/mcp, and when asked about custom headers add Authorization = Bearer <your dev key>. A one-off session via goose session --with-streamable-http-extension works too, but the CLI flag has no header slot — use it only with the paid gate or paste your key via configure.

Why the header is required: the gateway is itself a paid x402 gate — a request with no Authorization gets an HTTP 402 payment challenge (scheme=exact, eip155:8453, canonical payTo). Goose cannot pay a 402 challenge itself, so the Bearer dev key is the Goose path; the key covers the tool metering instead.

Path 2: raw x402 from a recipe script (wallet-native)

For headless runs, cron recipes, or when you want payment to be the wallet's signature rather than a metered key, call the endpoints directly with the two-POST 402 flow from a script step (Goose recipes can run shell/Python steps; an inline_python extension works the same way):

import json, requests

def x402_call(url: str, body: dict, signer) -> dict:
    # 1) trigger the challenge
    r = requests.post(url, json=body)
    if r.status_code != 402:
        return r.json()
    challenge = json.loads(r.headers["payment-required"])  # contains accepts[]
    # 2) sign the exact-scheme challenge with your Base wallet (EIP-3009
    #    transferWithAuthorization on USDC), then re-send with the payment header
    sig = signer.sign_challenge(challenge)
    r2 = requests.post(url, json=body, headers={"PAYMENT-SIGNATURE": sig})
    return r2.json()

# Goose recipe step: scripts/govx402.py --law-lookup "FDCPA section 1692g"

Any EIP-3009 signer works. Copy-paste client recipes: x402-cookbook (recipe 02 is the Python client).

Why Goose fits

Goose extensions are MCP servers, and the RAEN gateway is a hosted MCP server — so "giving Goose paid tools" is one config block, not a client library. Goose's env_keys substitution keeps the key out of dotfiles. And if you outgrow the metered key, Path 2 keeps payment wallet-native (EIP-3009) with no code change to the recipe's business logic — only the signer changes.
